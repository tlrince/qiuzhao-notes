# R2 v2 迁移与存储验收

状态：已完成。R2 在 R1 领域契约上新增完整 v2 快照和双端持久化适配器；随后 M3 v2 已将当前业务页面切换到 v2 Repository。

## v1 → v2 迁移

- 工作空间、招聘季、渠道、岗位元数据、日程及稳定 ID 保留；`jobUrl` 原样保留，`trackingUrl` 初始化为空。
- `assessment` 映射为 `written_test`，旧单阶段事件的 phase 保持 `unknown`，并以 `legacyReached` 保留旧版已记录触达这一事实；不推断通过。
- `interview_3_plus` 映射到归档环节 `legacy_interview_3_plus`，显示“三面及以上·待确认”，不猜具体轮次。
- `rejected` 映射为 `failed` 与 `failedAt=unknown`；`offer` 映射为 `offer_received`；`withdrawn` 继续保持主动退出语义。
- 阶段事件和结果事件的原始数组、来源 ID、失效时间及原始内容都保存在 `legacyHistory` 与事件迁移元数据中。数组内部顺序保留，跨数组合并不读取 `createdAt`。
- 同日或日期/源数组顺序冲突会标记 `uncertainEdges`，投影保留这些连接供 UI 画虚线和提示用户确认。v1 曾记录终态后恢复进行中但没有显式 reopen 的记录也会标记待确认，不补写重开原因。
- v2 快照校验会校验定义引用、应用关联、投递日期、失败归因和有效事件链尾投影；损坏或与旧当前状态不一致的输入不会生成部分快照。

## 双端持久化

- `SnapshotStoreV2` 使用全量快照与全库 revision CAS；校验失败或 revision 冲突不会改变已提交快照。整快照替换也作为原子恢复入口。
- IndexedDB 从物理版本 1 升至 2，在单次 versionchange 事务内迁移、写入 v1 恢复副本及新快照；任一错误都会回滚整个升级。新 adapter 在提交事务完成后才发 BroadcastChannel 通知。旧 v1 adapter 因版本不符或逻辑 schema 不符而拒绝写入。
- SQLite 单独维护物理 schema 版本与逻辑快照版本。Rust 命令在事务内执行 revision CAS 和 v2 校验，升级前保存同 revision 的 v1 恢复快照；v2 校验失败、revision 过期或 SQL 错误不会替换当前快照。旧写命令只接受逻辑 v1。
